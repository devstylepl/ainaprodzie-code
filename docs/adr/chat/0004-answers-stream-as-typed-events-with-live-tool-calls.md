# The chat streams its answer as typed events and shows tool calls as they happen

A question goes to `POST /api/chat/conversations/{conversationId}/messages`, and the answer comes back as a `text/event-stream` of typed events: `reasoning` for each piece of the model's reasoning, `toolStarted` when the model begins to write a tool call, where the provider streams it, `tool` when the model calls a tool (its name and the arguments the model chose), `token` for each piece of the answer text, then `done`, or `error` with a code. The events are one sealed `ChatEvent` type in Java and one `oneOf` schema with a discriminator in the OpenAPI contract, so the SPA's types still come from the contract. The SPA reads the stream with `fetch` and a `ReadableStream`, because `EventSource` can only send GET and cannot carry the CSRF header.

Tool calls reach the stream through an advisor ordered inside Spring AI's `ToolCallingAdvisor` loop. Spring AI 2.1 filters a complete tool call out of what the caller of `stream()` sees and passes on only the partial parts of a call the model is still writing, and an advisor inside the loop is the documented way to report a complete call to a UI. The same `tool` events are what the evaluations (chat ADR 0003) assert tool calls on, so the UI and the evaluations observe one mechanism.

A provider that streams a tool call while the model writes it adds a `toolStarted` event before the call's `tool` event. It carries the tool's name and `toolCall`, the position the call's `tool` event will have among the turn's `tool` events. The trace shows the call's step from that moment, and the `tool` event gives the step its arguments in place. The advisor sends `toolStarted` once per call, at the first partial `ToolCallPart` Spring AI 2.1 makes of the provider's argument deltas, and reads only the name from it: the arguments so far are unfinished JSON that may hold placeholders (chat ADR 0009). A call the model never finishes has a `toolStarted` and no `tool` event, so the evaluations do not count it. Through LiteLLM, Anthropic streams a call 0.3 to 0.6 s before it is complete, and Gemini sends it whole, a few milliseconds after its only partial part (jkubrynski/retrofit#330).

The reason is the lesson. A participant sees, on screen, that the model does not know the data: it asks for a tool with arguments it picked, and the signed-in user's id is never one of them (chat ADR 0002). An answer that streams in after visible tool calls is also what makes the chat look different from a search box in the first minute of the demo.

## Considered Options

- **One JSON response when the answer is complete.** This was rejected because a conversation with two or three tool calls leaves the user looking at a spinner for several seconds, and the tool calls, the most instructive part, stay invisible.
- **The chat runs the tool loop itself** (tool-calling advisor disabled, `ToolCallingManager` called by hand). This was rejected because it repeats what the advisor already does, and Spring AI's documentation calls it verbose and outside advisor composition and observability.
- **Reading the start of a call at the caller of `stream()`.** Spring AI 2.1 passes the partial parts there, and its documentation shows that for a UI. This was rejected because the complete call is still visible only inside the loop: the two events of one call would come from two places, away from the count of calls that numbers them.
- **A state on the `tool` event**, sent once without arguments and once with them. This was rejected because every reader of `tool`, the evaluations first, would have to tell a call from its start.
- **Micrometer observations of tool calls.** They suit metrics and tracing, but they are no channel back to the one HTTP stream that asked.
- **WebSocket.** This was rejected because the conversation is one request and one streamed answer. Nothing flows from the browser while the answer streams except a cancel, which closing the request already expresses.

## Consequences

- A failure before the stream starts (validation, authentication) is an ordinary `ProblemDetail` with its status. Once the stream has started the status is already 200, so a later failure is an `error` event whose code (`rate-limited`, `unavailable`, `timeout`, `guardrails-blocked`, `failed`) the SPA turns into a translated message.
- The advisor's loop limits the steps of a turn, not its time: `spring.ai.tools.limits` ends a turn at its seventh tool call, and `spring.ai.openai.timeout` bounds one model call. The whole turn has one deadline too, `retrofit.chat.turn-timeout`, applied to the stream in `ChatService` and shared by every element, so a steadily streaming model cannot outrun it. Past it the turn ends with the `timeout` code. The deadline cancels the stream but not a tool already running.
- An `EventSource` can no longer be the client. The stream needs the CSRF header but not the rest of `api()`, which today builds the headers and calls `fetch` in one function. A refactor of the SPA's API module extracts the header building into an exported function that `api()` and the stream both call, so the stream does not read the cookie a second time.
- Streaming went through LiteLLM's OpenAI emulation of Gemini in a check against a mocked provider. The first tool's end-to-end check (chat ADR 0002) repeats it against the real provider before the rest of the chat is built.
