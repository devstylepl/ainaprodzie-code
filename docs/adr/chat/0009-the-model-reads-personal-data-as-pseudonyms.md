# The model reads the people the app knows as pseudonyms, and the user reads them back in full

This holds while support staff keep "Mask personal data in the app" on (chat ADR 0018); off, no person gets a placeholder, the model reads questions and tool results with their names, and only LiteLLM's guardrail masks anything. Two rules hold in both states, and say so below: what the model writes is read back, and a text that only looks like a placeholder is a value of its own.

The app replaces the people it knows with placeholders before the model reads a question or a tool result, and calls no Presidio to find them. It knows two kinds of people from its own data:

- **The people a tool result names in its own fields**: a ticket's author and assignee, a comment's author, a change's actor, and the assignees before and after an assignee change. Their names are replaced in the result's other texts too, as written.
- **The people of the directory**: the display names of the people the asker may see (`OrganizationAccess#displayNamesVisibleTo`). A customer sees the customers of their organization and all support staff; support staff see everyone. Disabled accounts are in it, as old tickets name them. The chat reads it once per question, and only with the switch on. A full display name of the directory is that name's placeholder in every text the model reads: the question and every text of a tool result. It is the placeholder a field of a tool result gives the same name.

A conversation keeps its placeholders: one name has one placeholder in every turn, so the model can tell two people apart and follow one through a conversation. "Bena Barkera" in the question and "Ben Barker" in the `assignee` field are one `<PERSON_1>`, because the placeholder stands for the directory's display name and not for the text the user typed. The placeholders live in the process next to the conversation's memory (chat ADR 0005), and forgetting the conversation forgets them, together with a turn still streaming when it is forgotten. A conversation nobody asks in for the idle timeout is forgotten the same way, so the names behind its placeholders do not outlive it.

A directory name matches when every part of it stands in the text in order, side by side, ignoring case, each with an optional Polish case ending from a closed list ("Bena Barkera", "Adamowi Novakowi"). An ending may replace a final "a" ("Grety Lind", "Gila Ortegi") of a part longer than that letter, so the "A" of "Jan A Kowalski" is not the word "i", and a part with a hyphen is one part, with the ending at its end. A letter or a digit beside the match makes it no match, and so does a hyphen with a letter beyond it ("Ann Lee-Smith" is somebody else's name). Where two directory names match the same text, the one the text writes as it stands wins over a case form of the other. One part of a name alone is no match ("Alice", "Sam" are ordinary words), nor is a display name of one word, unless a field of a tool result gave that name: then it is replaced as written, as every name a field gave. `PeopleDirectoryTests` holds every name of the demo data in five cases, each form as found or as missed.

The chat puts the names back wherever the user reads what the model wrote. The answer's tokens are restored as they stream, holding back an unfinished placeholder until its end arrives. A tool's arguments are restored before the tool runs, so a search for `<PERSON_1>` searches for the name, and the `tool` event shows the user the restored arguments. Memory keeps what the model read and wrote, with the placeholders, so a later turn sends the model nothing it has not already been spared. A switch changed during a conversation rewrites nothing: the earlier turns stay as the model read them. So the names are put back in both states of the switch: after it is turned off, memory still names a person by `<PERSON_1>`, a tool the model passes that to searches for the name, and the user reads the name.

Only the placeholders the chat gave out are put back. A text the model reads that only looks like one, such as `<PERSON_2>` in a log the user pasted or in a ticket's description, is a value of its own with a placeholder of the type `PLACEHOLDER`, such as `<PLACEHOLDER_1>`. The user reads that text as it was written, and a tool searches for it, never for the person the conversation gave `<PERSON_2>` to. This holds in both states of the switch too, in the question and in every text of a tool result, because a conversation keeps the placeholders it gave out while the switch was on.

An e-mail address, a phone number, an IBAN and a PESEL are the gateway's (chat ADR 0017), in both states of the switch. LiteLLM's guardrail replaces each with its type, such as `<EMAIL_ADDRESS>`, before the request reaches the provider and restores nothing, so the user reads `<EMAIL_ADDRESS>` in the answer; that shows the masking worked. A card number refuses the request instead. The guardrail looks for no people.

A Presidio that does not answer ends a question at the gateway: the guardrail calls the same two containers and fails closed, so the user reads `unavailable` in both states of the switch. The app's part is that it calls no Presidio on the question's path, and a regular test holds it.

The reason is the lesson: the training promises that personal data is protected before it is sent to the model, and the part the app can do reliably is the people its own data names. Masking alone was rejected in chat ADR 0007 because the user may read their own tickets and a masked tool result makes the answer wrong. Pseudonyms remove that objection: the model reasons about `<PERSON_1>`, and the user reads the name.

## Considered Options

- **Masking with the type alone** (`<PERSON>`), as the traces do. This was rejected because the user who asks whom their ticket names gets `<PERSON>` instead of the name, and two people in one ticket become indistinguishable to the model.
- **LiteLLM's Presidio guardrail instead of the chat** (`pre_call`, with `output_parse_pii` to restore the answer). This was rejected after a check on a running LiteLLM 1.108.3 in front of a provider that recorded what it received. To restore an answer, the guardrail waits for the whole stream and sends it as one chunk, so the user reads nothing until the model has finished. It numbers its placeholders afresh in every message, so a person in the question and another in a tool result both become `<PERSON_1>`, and the user reads one name for both. It masks tool results but not the tool calls of earlier turns, whose arguments it has restored, so a name the model searched for reaches the provider in the next call. It cannot be given an allow-list. Without restoring, support staff who ask for a customer's account would read `<IBAN_CODE>`, and the traces (chat ADR 0007) would still need the app.
- **Presidio's analyzer on every question and tool result**, which this decision was until #327. It was rejected after a measurement of twelve questions, 8 asks each, on `chat-gemini`: with the switch on 55 of 96 answers were right and readable, with it off 70 of 96 (#325). Its English model finds `PERSON` badly in Polish text and takes ticket references and product names for people, which needed an allow-list. A finding is a text, so "Bena Barkera" in the question and "Ben Barker" in a field were two people, and the model answered "Nie, …" in 8 of 8 asks whether Ben Barker was the assignee. It also made every question and every tool result wait for the analyzer, and a Presidio outage end the question in the app as well as at the gateway.
- **A person's id from the database** (such as `user:<id>`), with the names of the people the asker may see matched in every text. This was rejected on `lesson-1`: the tool results carry no ids, an assignee change keeps its assignees by name only, and no tool takes a person here, so the model has nowhere to pass an id. An id that stays the same in every conversation also lets the provider link one person across conversations, which a placeholder numbered per conversation does not. From `lesson-2` on the placeholder stands for a person by the id a tool result gives (that branch's copy of this decision).
- **The names of the question only, not of the tool results.** This was rejected because a person named in a description would reach the provider while no field of the result names them, and "przekazałem Benowi Barkerowi" in a comment would stay a name beside the placeholder of the `assignee`.
- **No directory: only the fields of a tool result.** This was rejected because a name typed into the question is read as a name beside `<PERSON_1>` in the field, and the model cannot tell they are one person. On `chat-gemini`, asked by support staff with the switch on, 8 asks per cell: "Czy autorem zgłoszenia RET-1042 jest Ian Chu?" was answered right 3 of 8 times as written and 8 of 8 with the directory, and "Czy zgłoszenie RET-1007 jest przypisane do Bena Barkera?" 0 of 8 and 8 of 8.
- **The field left as text when the question has already named its person.** This was rejected because the people fields would not keep their placeholders, and the name in the question still reaches the provider.
- **A sentence in the prompt telling the model to say who the field names instead of yes or no.** This was rejected because it never answers yes, and 2 of 8 answers about Ben Barker still deny.
- **A directory of everyone for every asker.** This was rejected: the asker typed the name, so the limit hides nothing from them, and it is the rule of `OrganizationAccess`, which answers what one caller sees. On `lesson-2` and later it matters more, because a placeholder there carries a person's id that the model may pass to a tool.
- **Pseudonymizing in the model call** (an advisor or a `ChatModel` wrapper that rewrites every request). This was rejected because the tool loop runs between those calls: the tools would receive placeholders as arguments, and the restoration would have to reach into the loop anyway.
- **Escaping a text that looks like a placeholder inside the text**, for example with a zero-width space after its `<`. This was rejected because the escape survives only if the model copies an invisible character, while copying a placeholder exactly is a rule it already follows.

## Consequences

- Nothing waits for Presidio on the answer's path, and the guardrail still looks through the whole request at the gateway (chat ADR 0017).
- Every text of a tool result is matched against every name of the directory, which for support staff holds everyone: the cost grows with the people and the texts of a result. The directory is read once per question.
- One placeholder stands for a name, not for a person, on `lesson-1`: two people with one display name are one placeholder.
- What the app does not protect, with the switch on:
  - a name of somebody with no account, in the question or in a ticket (Jan Kowalski in RET-1027);
  - a name of a person the asker may not see;
  - one part of a name alone, and a display name of one word that no field of a tool result has given;
  - a name written in another order than the display name or with a word between its parts ("Barker Ben", "Ben T. Barker");
  - a Polish case form that changes the name's stem ("Grecie", "Ortedze", "Supporcie");
  - the earlier turns of a conversation begun with the switch off, which memory keeps as the model read them;
  - addresses and identifiers outside the gateway's entities ("ul. Prosta 12", "employee ID 88231"), and the names of organizations and teams, which are not personal data.
- With the switch on, a question that names a person in a form the directory misses and asks whether they are a ticket's author or assignee may be answered "no" wrongly.
- A name that is a directory name plus a case ending is read as that person: with "Ann Lee" in the directory, a user who types "Anna Lee" reads "Ann Lee" back, because a closed list of endings cannot tell a case form from the name of somebody else. `PeopleDirectoryTests` pins it.
- An e-mail address, a phone number, an IBAN or a PESEL cannot be read back through the chat, in both states of the switch: the user reads the gateway's marker, and the ticket's page shows the value.
- The same four, typed into the question, cannot be searched for or written through the chat: the model passes the marker to the tool, so `searchTickets` looks for the text `<EMAIL_ADDRESS>`.
- The model must copy a placeholder exactly. The system prompt tells it so in one rule for both states of the switch, because the prompt is a static prefix (chat ADR 0008): personal data may be replaced by placeholders, with a number or without one, and the model writes none that it did not read. The rule shows no placeholder as an example: with `<PERSON_1>` and `<EMAIL_ADDRESS_1>` as its examples the model wrote `<PERSON_1>` for an assignee it had read by name, in 9 of 10 Polish answers with the switch off, and numbered the gateway's marker in 3 of 10 answers. It keeps the opening of the rule it replaces, personal data that may be replaced: a rule that opened with what a question or a tool result may hold made the chat of `lesson-3` refuse "Move RET-1050 to the accounts team" in 6 of 10 answers instead of asking which team is meant (#339). Nor does it say that a name read as text is written as that text: with that sentence added the same question was refused in 2 of 6 answers, and without it the model names the assignee it read by name in 10 of 10. The evaluations check that answers name the people the tickets hold, with the switch on and with it off.
