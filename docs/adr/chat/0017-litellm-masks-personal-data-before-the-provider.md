# LiteLLM masks personal data before a request reaches the provider

A question can hold a customer's email address, phone number, IBAN, card number or PESEL, and the chat sends it to a model provider outside the app. LiteLLM's Presidio guardrail (`personal-data` in `litellm/config.yaml`) looks through every request on every alias the app calls before it leaves the proxy. It replaces an email address, a phone number, an IBAN or a PESEL with its type, such as `<EMAIL_ADDRESS>`, and blocks a request holding a card number with 400 "Blocked entity detected: CREDIT_CARD". The chat ends such a question with the error code `guardrails-blocked` (chat ADR 0004): the SPA says that the question was not sent, that personal data such as a card number is the reason, and what to do, and offers no Try again, as the same question would be refused again. It restores nothing. The `presidio-analyzer` and `presidio-anonymizer` services in `compose.yaml` do the finding and the masking. The analyzer loads the recognizers of `presidio/recognizers.yaml` in place of its defaults: names, card numbers, emails, IBANs, phone numbers and Presidio's own PESEL recognizer, which it loads only for Polish by default and is listed there for English, the language every caller asks in. That recognizer checks the checksum, so an 11-digit number of a PESEL's shape that is no PESEL stays as it is. `litellm/presidio-recognizers.json` adds an email address under any top-level domain, as Presidio's own misses the demo data's `.example`. A test holds the guardrail to every alias in the app's access group, to its entities and to its class, which `compose.yaml` mounts next to LiteLLM's config, and the analyzer to the PESEL recognizer for English.

The guardrail's class is `litellm/personal_data_guardrail.py`: LiteLLM's Presidio guardrail with one rule added, that a card number found whole inside an IBAN is no finding. Presidio finds one inside some IBANs: in `PL61 1090 1014 0000 0712 1981 2874` of RET-1045, the 16 digits after `PL61` start with 1 and pass the Luhn check. LiteLLM's own guardrail refuses a request for a card-number finding wherever it lies, although the anonymizer masks the whole IBAN, and no option of LiteLLM or of the analyzer drops a finding that lies inside one of another type. With the rule, such a request goes on with `<IBAN_CODE>`. A card number anywhere else still refuses the request: beside the IBAN, overlapping it in part, or inside an email address or a phone number. `litellm/test_personal_data_guardrail.py` holds the rule through LiteLLM's own `check_pii` in the image `compose.yaml` pins, run by `PersonalDataGuardrailClassTests`, so an upgrade that stops calling the overridden method fails the build.

LiteLLM gives the refusal no code or type of its own: it is a 400 of type `invalid_request_error`, like a request for an unknown model. The app therefore tells it from another 400 by how its message starts, "Blocked entity detected:" (`ChatErrors`), and any other 400 stays `failed`. The same Python test holds those words in the pinned image, so an upgrade that rewords the refusal fails the build, where the chat would otherwise fall back to the generic failure unnoticed.

It fails closed: when Presidio does not answer within 2 seconds, the request fails and the provider receives nothing.

The reason is the course's order: the environment of `lesson-0` already sends what a user types to a provider, so it protects that before the chat reads any ticket. The proxy is the one place every model call passes, so the app needs no code for it.

## Seen in the live check

Against the compose stack on `chat-gemini`, asked to repeat a text: "Mail ian.chu@initech.example, PESEL 44051401359, call +48 601 234 567, Ian Chu on RET-1045, Taskline" came back as "Mail <EMAIL_ADDRESS>, PESEL <PL_PESEL>, call <PHONE_NUMBER>, Ian Chu on RET-1045, Taskline". With `presidio/recognizers.yaml`, "PESEL 44051401359, not a PESEL 44051401358" came back as "PESEL <PL_PESEL>, not a PESEL 44051401358". A card number gave 400 `Blocked entity detected: CREDIT_CARD by Guardrail: personal-data`. With `presidio-analyzer` stopped, LiteLLM answered 500 and called no provider.

On `chat-chaos`, whose provider logs what it receives: "Our account: IBAN PL61 1090 1014 0000 0712 1981 2874" reached it as "Our account: IBAN <IBAN_CODE>". "Card 4111 1111 1111 1111", alone or after that IBAN in one question, gave the same 400 and reached no provider. With `guardrail: presidio`, the IBAN alone gave that 400 too. With a copy of the class that looked for a method LiteLLM's guardrail does not have, LiteLLM did not start ("Could not import PersonalDataGuardrail").

On LiteLLM v1.108.8, with the app's key: a streamed request with "Card 4111 1111 1111 1111" as the question gave 400 with the message "Blocked entity detected: CREDIT_CARD by Guardrail: personal-data. This entity is not allowed to be used in this request." The same number in an earlier assistant message, under a question without one, gave the same 400. In the SPA the question ended with the personal data message and no Try again, and the app's log held `GUARDRAILS_BLOCKED` and no card number.

## Considered Options

- **Masking people too (`PERSON`).** Rejected: Presidio's English model takes ticket references and product names, such as `RET-1045` and Taskline, for people, and the guardrail cannot be given an allow-list, so the model would read questions it cannot answer.
- **Restoring the answer (`output_parse_pii`).** Rejected: to restore, the guardrail waits for the whole stream and sends it as one chunk, so the user reads nothing until the model has finished. It also numbers its placeholders afresh in every message, so two people of one type would read back as one.
- **A PESEL pattern of our own** (`presidio_ad_hoc_recognizers`), with Presidio's regex. Rejected: an ad hoc recognizer has a pattern and no validation, so every 11-digit number of a PESEL's shape is masked; Presidio's recognizer checks the checksum.
- **Presidio's default recognizers with the PESEL added.** Rejected: the registry file replaces the defaults, so adding one means copying all of them, tied to the image's version; the list holds only what is asked for.
- **Masking card numbers too (`CREDIT_CARD: MASK`).** Rejected: the IBAN would pass, as the anonymizer keeps the wider of two findings, but a request with a real card number would reach the provider masked instead of being refused.
- **Any wider finding excusing a card number**, an email address or a phone number as well as an IBAN. Rejected: the IBAN is the only case seen and its checksum makes the wider finding trustworthy, while Presidio's phone recognizer is lenient and would turn refusals into masks.
- **The rule in the analyzer.** Rejected: the registry file gives Presidio's card recognizer no pattern of its own, and a pattern of ours has no Luhn check. A recognizer class of ours has to come in through a mounted `gunicorn.conf.py`, and it would change what every caller of the analyzer finds, where only LiteLLM's refusal is wrong.
- **A code named for what the guardrail looks for (`personal-data-blocked`).** Rejected: the code says what happened, LiteLLM's guardrail blocked the request, and the message says what was found. The message and the words `ChatErrors` knows the refusal by are those of `personal-data`, the only guardrail that blocks; another guardrail's refusal would end as `failed`.
- **The blocked entity's type in the `error` event**, so the message names what was found. Not built: a card number is the only entity that blocks, and the message names it as the example.
- **Masking in the app.** Not on this branch: the chat reads no tickets yet, and the proxy covers every alias without code. The read-only chat adds the app's own masking, which the user reads back as the values.

## Consequences

- A name reaches the model, as the guardrail does not look for people.
- The model reads `<EMAIL_ADDRESS>` where the user wrote an address, and may answer with the placeholder.
- The guardrail looks through the whole request, the earlier turns included. A card number the model wrote in an answer is remembered with the turn, and every later question of that conversation is refused. The message therefore speaks of the conversation, and a new conversation is the way out.
- Every model call waits for Presidio, and a Presidio outage makes the chat fail, not only its masking.
- LiteLLM's spans in Phoenix and its Logs show the request as the provider received it, masked.
- Presidio's default NLP model is English; the guardrail's patterns do not depend on the language.
- The class overrides `filter_analyze_results_by_score`, a method inside LiteLLM's guardrail through which the findings pass before it refuses or masks. A LiteLLM upgrade repeats the IBAN and card requests of the live check; if the method is gone, the class does not load and LiteLLM does not start.
- LiteLLM builds a guardrail class of ours for the input only, which is all this guardrail looks through.
