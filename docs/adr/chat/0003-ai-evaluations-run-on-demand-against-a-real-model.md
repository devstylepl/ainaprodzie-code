# AI evaluations run on demand against a real model

Prompts, tools and model choices are checked by evaluations: suites that send real conversations through the real chat stack to a real model and check what comes back. They need a provider key, cost quota and are not deterministic, so they never run in `./mvnw verify` or by default in CI. A developer runs them on demand with `./mvnw test -Peval`. The regular tests keep stubbing the `ChatModel` (chat ADR 0002), and they cover everything that does not depend on what the model says.

- **Where they live.** An eval suite is an `*Eval` class tagged `@Tag("eval")` in the package of the feature it evaluates (`app.retrofit.chat` first, triage later). Surefire excludes the tag by default, and the `eval` profile runs only that tag.
- **One class per lesson.** Each lesson's feature adds its cases to an eval class of its own, numbered from 1 and writing a report of its own; the chat's classes extend `ChatEvalSupport`, which holds the context, `ask()` and the judge, and `ChatEval` holds `lesson-1`'s cases. A merge forward therefore never renumbers cases, and a case keeps its number, its surefire selector (`ChatEval#case11`) and its line in a report from one branch to the next. A lesson changes an earlier lesson's case in place only when the expected behaviour changes; a conflict there is a real disagreement between the branches, resolved by hand.
- **How they reach the model.** The eval context starts LiteLLM in Testcontainers with the same pinned image and `config.yaml` as `compose.yaml`, and passes the provider key the alias needs from the environment. Evals therefore exercise the same alias, proxy and provider as the running app, independent of whatever stack is running locally. On another provider they show whether that model handles the tools. A missing key fails the run with a message naming the variable. Skipping would report an eval nobody ran as green.
- **What they run against.** The demo data, because its similar tickets, vague descriptions and prompt injection attempts are what the chat and triage have to handle. This is a deliberate exception to the test standard that tests see the schema and never the dev seed. The seed's timestamps are relative to the moment it runs, so expectations never contain absolute waiting times or deadlines. They name tickets, statuses and whether the SLA is breached.
- **How they check.** Each case is one parameterized test and states what must hold: which tool was called with which arguments, which facts appear in the answer, and which data must not appear (another organization's tickets, internal notes for a customer). Direct assertions come first. An LLM judge (Spring AI's evaluators) is used only for qualities a direct assertion cannot check, because each verdict costs a request and is not deterministic either.
- **Who judges.** The judge runs on an alias of its own, `judge-gemini` (`gemini-3.8-flash`) unless `JUDGE_MODEL` names another, such as `judge-anthropic` (`claude-sonnet-5-5`), and the report names it, with the model that answered (below). It is a stronger model than the one it grades, because a judge as weak as that model misreads its criterion: Gemini 3.5 Flash-Lite, judging answers of its own, passed one that the criterion quoted as a failure 3 times in 5, where Haiku never did. `judge-gemini` needs no key beyond the chat's, so a participant's free Gemini key runs the evaluations, within that model's smaller daily quota.
- **Which model answered.** An alias says which entry of `config.yaml` was asked, and that entry's provider model changes with the file, so two reports with one alias and one prompt version may describe different models. The first line of a `ChatEvalReport` therefore names, after the chat's alias and after the judge's, the provider model that answered for it in that run: `model alias chat-anthropic (anthropic/claude-haiku-5-5)`, `(mixed: …)` with the models in the order they first answered when more than one did, `(not called)` when none did. The name is LiteLLM's response header `x-litellm-model-name`, which the evaluations' test code records from every 2xx response under the alias its request named (`AnsweringModelRecorder`): a response a fallback answered no longer names the alias that was asked. A case whose chat alias or judge alias was answered by a model that `config.yaml` does not name for that alias fails, for the reason a missing key fails the run: a green report would describe a model nobody evaluated, and `disable_fallbacks` did not hold (chat ADR 0019). Two entries under one alias are no failure: the line says `mixed` and the cases keep their results. Other aliases a run calls are recorded and not held to the file, because the header was measured on chat completions only.
- **Quota.** A tool-using conversation makes several model calls, and free tiers (Gemini's among them) limit requests per minute. Evals run sequentially with a configurable delay between cases, so a run on a rate-limited key fails on answers rather than on HTTP 429.

Triage comes with its own evaluation dataset with expected classifications (requirements, section 7). Scoring it across the dataset, instead of case by case, is decided together with triage.

## Considered Options

- **Evals inside `./mvnw verify`.** This was rejected because every build would need a key and quota, and a build that goes red because the model answered differently teaches people to ignore red builds.
- **Evals against the LiteLLM from `compose.yaml`.** This was rejected because the eval run would then depend on whatever stack happens to be running, and that stack's port changes with every container restart.
- **The judge on the evaluated alias.** This was the first design, rejected once the default chat model proved too weak to judge (see above): a verdict that changes with the model under test cannot tell a worse answer from a worse judge.
- **One `ChatEval` numbered along the branch chain.** This was the first layout, rejected after two merges forward (#164, #234): a case added on `lesson-1` took a number `lesson-2` already used, so every merge renumbered `lesson-2`'s cases inside the conflict, and "Case 22" before the merge and after it were different cases.
- **The provider model read by the app, as an attribute of its model span.** Not built: the app knows aliases only (chat ADR 0002), and LiteLLM's span under the app's span already names the provider model (chat ADRs 0015 and 0016). The header is read in the evaluations' test code, and nothing under `src/main` reads it.
- **The provider model taken from `config.yaml`.** Rejected: the file says which model should answer, and the report must say which one did.
- **A pass-rate threshold per suite.** This was rejected for the chat because with 10 to 20 cases one case moves the rate by 5 to 10 points, and JUnit reports cases, not rates.
