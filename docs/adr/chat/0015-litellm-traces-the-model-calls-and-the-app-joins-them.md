# LiteLLM traces every model call, and the app joins its spans to them while support staff allow it

The chat is traced twice. LiteLLM reports every model call to Phoenix through the callback of chat ADR 0014 (`litellm/phoenix_callback.py`, LiteLLM's `arize_phoenix` pricing each call once), so a call is priced from the provider's own model name whatever the app does. The app adds its own spans (the HTTP request, the chat client, the model and tool steps) only while a switch that support staff set on the Settings page says so, and then the two are one trace. This answers part of chat ADR 0007, which rejected tracing in LiteLLM because it cannot see the tools the app runs between model calls: LiteLLM alone is now the default, and the tool steps are one switch away.

Both sides write to one Phoenix project, `retrofit`: the app through the resource attribute `openinference.project.name` in `application.yml`, LiteLLM through `PHOENIX_PROJECT_NAME` in `compose.yaml`. This supersedes the project of its own that chat ADR 0014 gave LiteLLM. That ADR rejected one project because a model call traced by both sides would be priced twice in it; the app's model span is no longer priced (`retrofit.chat.tracing.model-names` is gone, L1), and a question's trace and its model calls can only be one trace inside one project.

## The switch

- **Stored.** One row in `chat_setting` (`app_traces_exported`, off in the changeset, a `CHECK` keeps it to one row), read through `GET /api/chat/settings` and changed through `PATCH`, a merge patch that names only the settings it changes; the others stay as stored, and the answer is every stored setting. A `PUT` of every setting was rejected: the Settings page sent its loaded copy, so a change of one setting undid what someone else had changed in another since the page loaded. Two changes of the same setting end as the later one; the settings carry no version. Only support staff may call it (`SecurityConfig` matcher, 403 `auth/forbidden` for a customer). A fresh database exports no app spans until support staff turn the switch on. An in-memory switch was rejected: it would forget the choice at each restart and differ between instances.
- **Global.** One value for the whole app, not audited, not per person.
- **Gate before masking.** `SwitchedSpanExporter` wraps `MaskingSpanExporter`. It reads the switch once per export batch, at export time, so spans batched before a change leave or drop by the state that holds when they are exported. Off drops the batch as a success before the masker sees it, so nothing goes to Presidio either. A switch that cannot be read counts as off. The store is looked up lazily, so the tracer provider does not bring the datasource up early. Gating the sampler was rejected: it decides when a span starts, so a change would not reach spans already batched, and a dropped span would break the trace's parent links instead of leaving them whole.
- **No `traceparent` while off, unless joined.** `ChatService` writes the header only while the switch is on, so LiteLLM's spans are roots then and show in Phoenix's trace list (below). A second switch, `gateway_traces_joined` ("Group LiteLLM calls per chat message" on the Settings page, off in its changeset), sends it while app traces are off too: LiteLLM's calls for one chat message then share that message's trace, whose app spans never arrive, so Phoenix lists each call as a row of its own, as its parent is missing (L9). With app traces on it changes nothing.
- **Settings traffic is not traced.** `onlyChatRequests` narrows from `/api/chat/` to `/api/chat/conversations/`, so loading or saving the Settings page never appears as a trace.

## The join

The `traceparent` header is written once per question, on the request thread, by Spring Boot's Micrometer `Propagator` from the question's HTTP request span, and rides on every model call of the question as a per-request custom header. An OkHttp interceptor on the OpenAI client (`OpenAiHttpClientBuilderCustomizer`) then rewrites it to the span of the model call that is going out, so each `litellm_proxy_request` hangs under the app's model span that made it. The header cannot carry the model span from the start: Spring AI builds the request, headers included, before it starts the model observation. Nor can the interceptor read the current span: the OpenAI client enqueues the call from `ForkJoinPool.commonPool()`, where no context is current, and Reactor's context propagation does not reach it. So `OpenModelCalls`, an observation handler, keeps the model calls under way, and the interceptor takes the one open in the trace the header names; a question's model calls run one after another, so a trace has at most one open. A request without a `traceparent` (the switch off, or no request span) stays without one. Seen with the switch on, before the rewrite: one trace of 14 spans, the HTTP root, the chat client, two model calls with a model span each, the tool call, and LiteLLM's two `litellm_proxy_request` spans with their `litellm_request` children under the root.

The propagator is registered only while tracing export is enabled (Spring Boot 4.1 registers the W3C propagator under `@ConditionalOnEnabledTracingExport`). With export off, as in the `test` profile, no header is written, and a test of the header turns export on.

## Seen in the live check

The check ran against the compose stack (LiteLLM v1.106.6, Phoenix 21.0.0, Presidio 2.2.365) with `chat-gemini`; `chat-anthropic` was not run (no key), so the price of `claude-haiku-5-5` was not checked.

- **Model name and price (L1).** LiteLLM's span names the provider model (`llm.model_name = gemini-3.5-flash-lite`, `llm.provider = gemini`) and carries `llm.cost.total`, and Phoenix prices it. The app therefore sets no `llm.model_name` and `retrofit.chat.tracing.model-names` is gone. Phoenix still derives `llm.model_name = chat-gemini` on the app's model span from `gen_ai.request.model`; the alias has no price, so that span costs nothing. The streamed chunks name the alias (L11), so the app span's response model does not become a second priced name.
- **Join (L2).** LiteLLM honours an incoming `traceparent`: its `litellm_proxy_request` has the sent trace id and the sent span as its parent, with message logging off too.
- **Forwarded headers and spend logs** (checked again on v1.108.3). The request headers LiteLLM keeps in its metadata leave out `Authorization`, so the app's key reaches neither Phoenix nor the spend logs. `turn_off_message_logging` also redacted the messages in the spend logs (`redacted-by-litellm`), which is one reason content was turned back on (below).
- **Metadata and user (L3).** `prompt_name`, `prompt_version` and `conversation_id` reach LiteLLM's spans in full as `metadata.requester_metadata.*`, and Phoenix filters on them (`metadata["requester_metadata"]["conversation_id"] == "..."`), so `config.yaml` names no allowlist. The app sends the caller's id as the request's `user`, a UUID that names no one by itself, so LiteLLM counts spend per end user (`/customer/info`) and Phoenix lists the calls by user. LiteLLM takes the request's `user` as its end user, which it puts on `session.id`, and copies the call's `user` parameter into `user.id` and `llm.user`; `config.yaml` drops that parameter before the provider (L12), so `user.id` falls to the key's user and `llm.user` is left off. `phoenix_callback.py` therefore sets `user.id` to the end user (`metadata.user_api_key_end_user_id`) and `session.id` to the conversation id, and puts both on `litellm_proxy_request` too, which is the trace's root while no `traceparent` is sent; the app's own spans carry the same `user.id` and `session.id`, and a conversation is one Phoenix session either way. Checked on v1.108.3, and on v1.108.8 for the dropped `user` (`arize/_utils.py`, and the spans a LiteLLM exports in `CallerIdTests`). LiteLLM also records the app's request headers as metadata (`user-agent`, `host`, the `x-stainless-*` client headers) and its key alias, budget and spend; no `Authorization` header and no key appear. The provider answered every request with metadata normally (L10).
- **Masking (L4).** LiteLLM's Presidio guardrail in `logging_only` mode did not do what its name says. It masked the phone number and the name `Jan` in the spans, left the e-mail address unmasked, and masked the response object in place in the success handler, so the caller received `call <PERSON> at <PHONE_NUMBER> ...` in a single chunk, streamed or not. That guardrail was not kept. Content was first switched off (`turn_off_message_logging: true`), then turned back on with `store_prompts_in_spend_logs: true`, so LiteLLM's spans and its admin UI's Logs show each prompt and answer. They hold what the provider receives: the app replaces the people it knows with placeholders before the call (chat ADR 0009), and LiteLLM's `pre_call` guardrail `personal-data` masks the pattern data (chat ADR 0017), so both read as placeholders; what neither found, such as some names in Polish text, is stored as written, in Phoenix and in LiteLLM's tables, with no retention limit. The provider sees the same text, so storing it adds places, not exposure to a new party. A guardrail on a deployment (L7) was accepted by LiteLLM but is not logging only either. The app's own spans stay masked by `MaskingSpanExporter` and its limits (chat ADR 0007), such as names in Polish text; one false positive was seen, part of a tool-call id masked as a PESEL.
- **Content attributes (L6).** The message attributes are present without `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`, so the variable stays unset.
- **Project (L5).** `PHOENIX_PROJECT_NAME: retrofit` alone puts LiteLLM's spans in project `retrofit`; no `LITELLM_OTEL_V2` is needed.
- **Orphans (L9).** A span sent without `traceparent` is its own trace and is listed by Phoenix's root-span filter (`parent_id is None`). A span whose parent never arrives is different: with the switch flipped Off before the app's spans were exported, a full queue, a failed OTLP export or the shutdown flush, LiteLLM's span keeps the app's span as its parent, and that parent is absent. Phoenix lists such a trace (`GET /v1/projects/retrofit/traces`, counted in the project's trace count) but not among the root spans, and the trace has no root.
- **The caller's id stays in the gateway (L12).** LiteLLM v1.108.8 hands `user` on to a model of OpenAI's catalog and to Anthropic, which receives it as `metadata.user_id`; Gemini and an OpenAI-compatible model outside that catalog, such as the chaos provider, never receive it. `additional_drop_params: ['user']` on each alias of the `app` access group keeps it from every provider an alias may name, and `PersonalDataGuardrailTests` holds the file to it. With it, an Anthropic API that records its requests (the test's stand-in for `chat-anthropic`) receives no `metadata`, where it received the caller's UUID before. `chat-chaos`, behind `openai/chaos`, never received `user`, so the provider's side of it shows nothing either way; its spans do show the drop: a question on it left LiteLLM's `litellm_request` span with `user.id`, `llm.user` and the end user before the parameter was dropped, and after it with the end user alone, as the app's key has no user for `user.id` to fall to. `phoenix_callback.py` sets `user.id` from the end user again (`CallerIdTests`, `PhoenixCallbackTests`), and `llm.user` stays off the spans.
- **Evaluation container (L8).** The evaluations' LiteLLM starts on the final `config.yaml`, case 13 passes, and the only export attempt was to `localhost:6006` inside the container (connection refused). No environment was added to `ChatEvalConfiguration`. The first run, with the `logging_only` guardrail, failed at start on the missing `PRESIDIO_ANALYZER_API_BASE`. `ChatEvalSupport` turns the switch on before each case, because the cases read the app's exported spans.

## Seen end to end

On a fresh compose database, as support staff, with a question that calls one tool (two model calls):

- `GET /api/chat/settings` answered `{"appTracesExported":false}`; a customer got 403.
- **Off.** Project `retrofit` held two traces, one per model call, and no app span. Each `litellm_proxy_request` was a root, carried the provider model, a cost and the metadata keys, and no content (it was off then).
- **On.** The switch was flipped on the Settings page. The question was one trace: the HTTP root with the chat client, model and tool spans, and LiteLLM's four spans under it, with the same metadata and still no content (it was off then). The app's model spans carried no cost. The app's spans were masked (`<PERSON_1>` in the tool result).
- **Cost and tokens.** LiteLLM emits two priced LLM spans per call, `litellm_proxy_request` and its child `litellm_request`, each with the call's full cost and tokens. Phoenix prices both, so every trace shows twice the cost of its calls (0.0014734 for a call that cost 0.0007367), joined or not. This was seen with the plain `arize_phoenix` callback; the callback of chat ADR 0014 leaves `litellm_proxy_request` a chain, so only `litellm_request` is priced. With the switch on, the app's model span still counts the call's tokens beside `litellm_request`, so a joined trace shows twice the tokens and the cost once.
- The header holds the Settings link, "Czat", "Wyloguj się" and the whole wordmark at 360px and 390px in both languages (the bar wraps; chat ADR 0001 lists the seam).

## Considered Options

- **A separate `litellm` Phoenix project** (chat ADR 0014). Superseded: see above.
- **Gating the sampler.** Rejected: see above.
- **An in-memory switch.** Rejected: see above.
- **A `PUT` of every setting.** Rejected: see above.
- **`traceparent` from the current span in the interceptor**, with the OkHttp dispatcher wrapped to restore the enqueuing thread's context and Reactor's context propagation on. Rejected: tried, and the OpenAI client enqueues from `ForkJoinPool.commonPool()`, where the model span is not current.
- **LiteLLM's Presidio guardrail, `logging_only`.** Rejected after the live check (L4): it altered the caller's answer.
- **The conversation's id as `user`, with nothing dropped.** Rejected: LiteLLM's end user and Phoenix's users would be conversations, and spend per caller would be gone, while `phoenix_callback.py` keeps the caller on the spans at the price of one line.
- **The caller's id as metadata only, with no `user`.** Rejected: LiteLLM has no end user then, so Phoenix's users and its spend per end user stay empty.
- **A metadata allowlist.** Not needed: the callback exports the keys unfiltered (L3). A comment in `config.yaml` says why none is named.

## Consequences

- With the default off, a fresh database sends no app spans; the README and the course agenda tell the instructor to turn the switch on to see the tool steps.
- A trace joined to the app's spans holds two counts of the same tokens and one of the cost (above), unless "App LLM traces to Phoenix" is off (chat ADR 0016).
- LiteLLM's spans and spend logs carry the pseudonymized prompts and answers, unmasked beyond what the app pseudonymized. The app's own spans, with the switch on, carry the same texts, masked by Presidio while "Mask personal data in the app" is on (chat ADR 0007) and as written while it is off (chat ADR 0018).
- LiteLLM's spans also hold the request headers the app sends and the app key's alias and spend. Nothing secret is among them today; a new header with a secret would reach Phoenix.
- No provider receives the caller's id: `additional_drop_params: ['user']` on every alias of the `app` access group keeps the request's `user` in LiteLLM, which would otherwise pass it to Anthropic as `metadata.user_id`, the same UUID in every conversation. An alias added to the group needs the line, and `PersonalDataGuardrailTests` fails without it. The caller's id still reaches LiteLLM's spans and spend logs, and Phoenix, as the end user.
- A trace whose app spans were dropped after the header was sent has no root and does not show among root spans.
- After a forward merge into a branch that adds LiteLLM calls the chat does not make, such as embeddings, those calls also reach project `retrofit`, and the merge decides whether they stay. The Settings link moves into the navigation that branch builds.
- Phoenix's built-in prices may lack `claude-haiku-5-5`, so the `chat-anthropic` path may stay unpriced; not checked.
